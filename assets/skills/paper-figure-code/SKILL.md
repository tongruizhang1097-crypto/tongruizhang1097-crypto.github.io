# 论文图码对照

面向深度学习初学者：根据任意论文（或本地论文/代码）先走统一的找代码流程，再交付可交互的「左代码 / 右模块图」双向对照。用中文向用户讲解模块，除非用户用另一种语言提问。

本配方对**任意论文**通用，不要为某一篇写死例外。Vision Transformer（arXiv:2010.11929）与 Swin Transformer（arXiv:2103.14030）仅在本地已有精修资源时可作为可选示例，不得当成必经路径。

## 不要做的事

- 不要把结果发布到公网临时网址或任何公开托管，除非用户之后明确要求部署。
- 不要编造仓库、源文件或对齐结果；公开检索没有可靠命中就如实说明。
- 找不到可展示源文件时，不要假装已经完成图码对照。
- 不要只丢一个外部仓库链接就算「找到了代码」：必须真正拉取可展示的实现源文件。
- 不要把用户的论文或代码上传到远程服务器；只在本机（或用户本机）处理。
- 不必调用付费大模型接口。启发式抽取与名称对齐即可。
- 不要在配方或对用户的说明里依赖某个助手名、某个临时站点或某一个人的 DOI。

## 输入

接受其中一种或组合：

- 论文标识：DOI（`10.…`）、arXiv 编号（如 `1706.03762`、`arXiv:1706.03762`）或论文链接。
- 用户给出的仓库或 `.py` 地址（GitHub / GitLab / Hugging Face / raw 或 CDN 上的源文件）。
- 本地文件：论文为 PDF / `.txt` / `.md`；代码为 `.py`、含 `.py` 的 zip，或整个文件夹。

建议上限（可按同样精神放宽，但先告诉用户）：论文约 40 MB，PDF 优先读前 20 页；zip 约 30 MB；单个 `.py` 约 40 万字符，且应含 `class` / `def` / `import`。跳过 `__macosx`、`node_modules`、`.git`、`dist`、`build`、`venv` 一类路径。

## 总流程

按顺序做，并向用户简要通报进度：解析标识 → 获取公开摘要或全文 → 抽取模块图 → **找代码** → 打开对照。只要还打算展示代码与模块的对照，就必须先完成显式的找代码步骤。

### 1. 解析论文

用公开元数据接口解析标题、作者、年份、摘要、刊物、开放 PDF 等，例如 OpenAlex、Semantic Scholar、arXiv，必要时再查 Crossref。识别不出论文时停止并请用户改输入，或改用本地文件。

若本地已有对应这篇论文的精修对照资源，可以直接使用，仍要标明来源；用户另外指定了仓库或上传了代码时，优先用用户提供的实现，不要 silently 丢掉。

### 2. 获取公开文本

优先开放的 arXiv HTML（官方 HTML 或同等 HTML 镜像），否则尝试开放 PDF（限制页数与体积）。拿不到全文时，只用标题、摘要和（如有）TLDR，并明确告诉用户：流程图主要依据公开元数据，细节会更粗。

本地论文：在本机抽取文本；若文中带有 DOI / arXiv，可再补公开元数据，但本地文本足够时不要因为元数据失败而中断。

### 3. 抽取模块图

从方法章节、小节标题、架构图题注里找具名模块，并与常见架构族（如 Transformer、BERT、ResNet、ViT、Swin、U-Net、GAN、扩散模型）的结构模板合并。每个模块需要：稳定 id、英文名、简短中文标题、面向初学者的中文讲解，以及模块之间的边。

自动图是启发式**结构草图**，不是论文官方原图。相关处用一句话说明，名称和边可能不完整或与作者用语不完全一致。封闭获取或只有摘要时尤其要标明。

不必调用付费 LLM。若公开文本里可抽取的模块名很少，做结构化兜底，并说明细节可能不完整。

仅有代码、没有论文时：跳到「只上传了代码」分支，不要虚构一篇论文。

### 4. 找代码（必须真正拉取源文件）

目标是得到可展示的模型源文件（通常是 Python），再按类名、函数名把模块对到行号。记录每一步尝试，最后向用户交代。

**来源优先级**

1. 用户提供的仓库或 `.py` 地址。
2. 从论文文本里收获链接：摘要、TLDR、元数据、全文 / arXiv HTML、论文已有的代码字段；若仍没有链接且有 arXiv 编号，再读 arXiv Atom 元数据。收获 GitHub / GitLab / Hugging Face 仓库和直接的 `.py` 链接。
3. 对空仓库、只有说明或没有可读 `.py` 的仓库：阅读 README，跟随「official implementation / 官方实现 / repo moved」等指向，最多约 3 次跳转。
4. 收获失败后再做目录检索兜底（见下）。**不要编造仓库。**

**目录检索（仅在收获未得到可展示源文件时）**

- 用论文标题做仓库搜索（匹配名称与描述）；若无可靠命中，再搜 `arxivId official implementation`（没有 arXiv 时用 `"标题" official implementation`）。
- 只接受与论文对得上的结果，例如：条目中出现该 arXiv 编号；或标题 slug / 显著词出现在仓库名或描述里，且标明 official 或有一定星标；不要把泛词（attention、transformer、model、official、implementation 等）当成足够证据。
- Papers with Code、Hugging Face 论文接口：仅当它们真正返回可用的结构化结果（如 JSON）时才采用其中的仓库链接；优先官方实现。接口不可用或无结果就记下并跳过，不要假装查到了。

**拉取与选择模型文件**

- 列出仓库中的 `.py`，按下方规则打分后拉取内容（可通过 raw / CDN 等公开地址）。每篇论文大约最多试 8 个仓库，每个仓库大约最多拉 8 个文件。
- 未认证的 GitHub 接口大约每 IP 每小时 60 次请求。遇到 401 / 403 / 429 时停止继续调用 GitHub 接口，记下「触发了访问限制」，改用已有链接、raw / CDN，或请用户提供地址 / 本地文件。
- 源文件必须含可读的 `class` / `def` / `import`，才能算可展示。
- 对齐：用模块 id、英文名等分词去匹配源文件中的类名与顶层函数名。对上则记下约 40 行以内的片段行号。自动对齐要标明，可能不完整；一个都对不上时，仍展示源文件中的主要类定义，并说明尚未按模块名精确对齐。不要把自动对齐说成人工精修。

**选择模型文件的打分（保持这一相对关系）**

- 文件名（去扩展名）与论文标题、架构族、仓库名等提示完全一致：高额加分。
- 路径或文件名包含提示词：中等加分。`models/` 目录、文件名含 model / modeling / transformer 及常见骨干名：加分；`model.py` / `models.py` 再略加。路径过深略减。
- `tests` / `docs` / `examples` / `scripts` / `tools` / `benchmarks` / `configs` / `ci` / `.github` 以及 setup、conftest、`__init__`、train、inference、demo、app、utils、dataset、dataloader、engine、optimizer 一类文件：大幅降权。
- `quantization` / `quant` / `tools` / `train` / `utils` 路径，以及量化相关文件名：惩罚，除非对齐明显更好（至少多对上 2 个模块）才可以压过当前候选。
- 先看对上的模块数（差距 ≥ 2 则取对齐更好的），再看路径分，再看对上数量。优先选非次要路径且已对上足够模块（大约不少于 3 个，或不少于 4 个）的文件。

### 5. 本地文件分支

文件只在本机处理，不要上传到远程服务器。

- **只有论文：** 抽取模块图，再走上面的找代码流程。
- **只有代码：** 按同一套打分选出模型源文件，根据其中的类和函数生成可用的模块图（说明模块图来自代码，不是论文原图），再对齐展示。
- **两者都有：** 从论文抽取模块，对齐到用户上传的代码（不必再为同一篇强制联网找代码，除非用户还要求核对公开实现）。
- 本地论文中若带有 DOI / arXiv，可用于补元数据或在「只有论文」时检索公开代码。

找代码失败后，继续请用户给出仓库 / `.py` 地址，或改用本地文件，然后从第 4 步恢复，不要丢掉已经生成的模块图。

### 6. 找不到可展示源文件时

不要打开对照页假装已经对齐。根据论文文本、已读到的 README、以及是否出现过仓库链接但拉不到文件，分成下面四种，并用中文明确告诉用户。判定时**优先 `not_open` 而不是 `coming`**：如 “available upon request / 应要求提供” 视为未公开，不要当成即将发布。

引用能找到的原文证据（「论文中的相关表述：…」），列出已尝试的步骤，然后请用户粘贴仓库或 `.py` 地址，或提供本地论文/代码。四种状态的用户可见文案：

**not_open — 这篇论文看起来没有公开实现**  
根据摘要或全文里的表述，作者没有把实现公开，或只在应要求时提供，因此公开渠道里读不到可对照的源文件。不会假装已经对齐代码。你可以给出已知的仓库或 .py 地址，也可以提供本地论文和代码来生成对照。

**coming — 论文提到代码将稍后公布**  
作者写明实现即将开源或稍后公布，但现在还读不到可展示的源文件。可以过一段时间再搜索一次，也可以现在给出已经公开的仓库地址，或提供本地论文和代码来生成对照。

**link_dead — 找到了仓库链接但拉不到源文件**  
论文或说明里出现了仓库地址，但仓库是空的、只是跳转说明，或拉取源文件失败。这不一定代表没有开源，也可能是链接失效或访问受限。请换一个仓库、直接给出 .py 文件地址，或提供本地代码。

**unknown — 公开渠道里还没找到实现**  
已经在论文文本、常见代码托管和公开检索里查找，但没有找到可靠、可展示的模型源文件，作者也没有明确说明是否开源。不会假装已经对齐代码。你可以给出仓库或 .py 地址，或提供本地论文和代码。

## 如何交付对照

这是与旧的网页托管的关键区别：默认交付用户能在本应用里打开、或作为本地文件打开的交互对照，而不是一个公网网址。

1. 先加载 Cursor 托管的 `canvas` 技能，再写 Page；不要跳过该技能自行猜测画布写法。
2. 页面布局：
   - 左侧代码（卡片或按模块切开的源文件片段，带行号）。
   - 右侧更宽、在滚动时保持可见（sticky）的模块流程图。
   - 中间可拖拽分栏；整页可以滚动。
   - 讲解面板在点击模块后保持可见（sticky）：中文标题、英文名、初学者讲解、可选形状说明、对应代码行号。
   - 点击左侧代码或右侧模块，两边一起高亮。
3. 页头给出论文标题、标识（arXiv / DOI）、所用源文件或仓库链接，以及自动对齐/摘要抽取等必要警告。
4. 若画布无法完全实现拖拽分栏或双向高亮，在 Page 上做到最接近的交互，并同时给出可在本地打开的对照文件；不要为此改去发布公网站点。
5. 幻灯片或静态导出只是次要选项，在用户明确要求时再做。

## 可选的本地工程

若运行环境里存在 `paper-figure-code` 工程（常见于 `/workspace/paper-figure-code`，或之后的拷贝），可以把它当作本地生成器或参考，复用其中的打分、抽取与对齐逻辑。该工程不在时，仍须用通用能力完成本配方：检索网页、获取论文与 PDF、列举并读取公开仓库、在本机读取用户文件、先加载 `canvas` 技能再写交互 Page。不要把该工程写成硬性依赖。

## 完成前自检

- 任意论文都走了同一套找代码，而不是某一篇的特例。
- 展示对照前已经拉取到可展示源文件，或已按四种状态之一如实说明失败原因。
- 没有编造仓库，也没有在未对齐时假装对齐。
- 自动图已按其是结构草图来说明（在相关时）。
- 用户文件未上传到远程服务器。
- 没有发布公网临时网址（除非用户后来明确要求部署）。
- 交付物是可交互的左代码 / 右模块图对照，讲解对初学者足够清楚。
